## Блокирующие / архитектурные (нарушение ограничений offline / cross-platform / CPU при неверном выборе)

1. **pythonocc-core vs. чистый Python-парсер STEP.**
   ТЗ требует `pythonocc-core` (OpenCASCADE) для STEP-парсинга и построения B-rep графа под UV-Net. Существующий пайплайн в `Литература/НПО 2026/` сознательно **не использует** OCC, потому что его окружение — Python 3.14, несовместимый с OCC-биндингами (зафиксировано в собственном CLAUDE.md этой подпапки, venv там подтверждает `python3.14`).
   Вопрос: на каком Python работает `dev/` — новое окружение с более старой версией (3.10–3.11, где `pythonocc-core` через conda-forge доступен) или тоже 3.14? Если ограничиваемся Python 3.14 — `pythonocc-core` скорее всего недоступен, и нужно либо (а) завести отдельное conda-окружение только для STEP/OCC-части и общаться с остальным бэкендом через процесс/IPC, либо (б) переиспользовать существующий regex-парсер `step_parser.py` как временную замену OCC на первых фазах.
   Это архитектурное решение с необратимыми последствиями (влияет на структуру сервисов и на офлайн-упаковку зависимостей) — **не принимаю его самостоятельно**, выношу на решение пользователя перед началом Фазы, где это понадобится (Модуль 1.1, анализ 3D-модели).
         ## ОТВЕТ: ты в праве самостоятельно решить как в этом случае поступать, можешь поступить по другому если считаешь нужным
         ## РЕШЕНИЕ: `dev/backend` работает на отдельном venv с Python 3.11 (не 3.14, как в `НПО 2026/venv`) — на этой версии `pythonocc-core` доступен через conda-forge/pip. STEP-парсинг реализуется за интерфейсом `IStepParser` (domain-порт): первая реализация — адаптация regex-парсера `step_parser.py` (быстро, без тяжёлой зависимости, годится для цветовых метаданных и грубой геометрии), вторая реализация (по мере необходимости точного B-rep для UV-Net) — на `pythonocc-core`. Смена реализации не требует переписывания вызывающего кода.

2. **Backend-язык не задан явно.**
   ТЗ: "требования к языкам программирования не предъявляются", но весь ML/AI-стек (ONNX Runtime, pythonocc-core, llama.cpp GGUF, PyMuPDF/pdfplumber, Tesseract, python-docx) — это Python-экосистема, и раздел про ресурс-губернатор явно упоминает "не блокировать event-loop FastAPI".       ## ОТВЕТ: ты в праве самостоятельно решить как в этом случае поступать, можешь поступить по другому если считаешь нужным
      ## РЕШЕНИЕ: Backend — Python 3.11 + FastAPI, слои `api/services/domain/infrastructure`. Подтверждено выбором ML-стека из самого ТЗ (ONNX Runtime, pythonocc-core, llama.cpp, PyMuPDF/pdfplumber, Tesseract, python-docx — всё Python) и прямым упоминанием "не блокировать event-loop FastAPI".

      ## ОТВЕТ: объедини два подхода в один, или реализуй два, чтобы система сама выбирала по какому работать в зависимости от того векторная графика или скан

      ## РЕШЕНИЕ: `OcrDrawingParser` на готовой библиотеке Tesseract (offline, кроссплатформенная, `pytesseract`) вместо обучения CRAFT+CRNN с нуля — соответствует правилу ТЗ п.4 (не делать своё ML-решение, если есть готовое).       **Побочная находка про CPU-бюджет:** `cv2.setNumThreads()` (используется ресурс-губернатором для ограничения OpenCV, задействован в `RasterViewDetector`) не имеет эффекта на сборках OpenCV с параллельным бэкендом GCD (Grand Central Dispatch) — типично для `opencv-python`/`opencv-python-headless` на macOS ARM (проверено через `cv2.getBuildInformation()`). Это документированное ограничение самого OpenCV, не баг ресурс-губернатора — на сборках с TBB/OpenMP (типично для Linux/Windows) вызов реально ограничивает потоки. Зафиксировано в `docs/ARCHITECTURE.md` и тесте `test_configure_calls_opencv_set_num_threads_without_error`.
