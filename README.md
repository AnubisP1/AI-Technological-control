# Система анализа КД и генерации технологической документации

Локальное, полностью офлайн приложение: анализ конструкторской документации (чертёж/спецификация/STEP) и CAD-моделей, генерация маршрутной/операционной карты, симуляция изготовления и контроль качества. Полная бизнес-логика — в `../Техническое задание.md`; архитектурные решения и план — в `PLAN.md`, `PROGRESS.md`, `docs/`.

⚠️ **Исключения из офлайн-требования** (Фаза 8/17, осознанное решение пользователя, см. `dev/QUESTIONS.md` №12): LLM-резюме отчёта КД (Модуль 1.2) и AI-ассистент по НСИ (экран "Обзор") опционально используют облачный YandexGPT API и требуют сети. Без настроенного ключа (см. "Требования" ниже) обе функции автоматически откатываются на офлайн-шаблонный текст — вся остальная система работает без сети как и раньше.

## Требования

- Python 3.11 (не выше — см. `docs/ARCHITECTURE.md`/`QUESTIONS.md` про совместимость с `pythonocc-core`)
- Node.js 20+ (проверено на 24)
- Tesseract OCR с языковым пакетом `rus` — для распознавания сканированных чертежей без текстового слоя (macOS: `brew install tesseract-lang`; Windows: установщик tesseract-ocr с выбором Russian). Не нужен для обычных векторных PDF-чертежей.
- (Опционально) Ключ YandexGPT API (`YANDEX_GPT_API_KEY`, `YANDEX_GPT_FOLDER_ID` в `backend/.env`) и доступ в интернет — только для LLM-резюме отчёта КД, см. предупреждение выше.
- (Опционально) отдельное conda-окружение с `pythonocc-core` — для точной тесселяции STEP-моделей в 3D-просмотрщике (Фаза 17, часть 5). Без него `PartViewer` показывает параметрический прокси-бокс по габаритам, как и раньше — не ошибка, задокументированный fallback. Установка (один раз, см. ниже).

### Установка pythonocc-core (опционально, для точной 3D-геометрии)

`pythonocc-core` не публикуется на PyPI (только conda-forge) — вызывается backend'ом как внешний интерпретатор через subprocess (см. `app/infrastructure/cad/step_mesh_exporter.py`), основной venv не изменяется.

```bash
# 1. Установить Miniforge (conda-forge дистрибутив conda):
#    macOS: brew install --cask miniforge (или https://github.com/conda-forge/miniforge)
#    Windows: установщик с https://github.com/conda-forge/miniforge
# 2. Создать окружение с pythonocc-core:
conda create -n pythonocc python=3.11 pythonocc-core -c conda-forge
# 3. Указать путь к python внутри этого окружения в backend/.env:
#    PYTHONOCC_PYTHON_PATH=/путь/к/miniforge3/envs/pythonocc/bin/python   (Windows: ...\python.exe)
```

## Анализ КД (Модуль 1.1)

```bash
curl -X POST http://localhost:8000/kd/analyze \
  -F "drawing=@чертёж.pdf" \
  -F "step_model=@модель.step"
```

Возвращает JSON с основной надписью, техническими требованиями и обнаруженными видами на чертеже, а также геометрией/цветовыми метаданными STEP-модели. Оба файла опциональны — для пластиковых изделий по ТЗ подаётся только `step_model`. Чертёж обрабатывается автоматически: векторный PDF — через текстовый слой, скан без текстового слоя — через OCR (нужен установленный Tesseract, см. "Требования"). Парсинг спецификации (БОМ) не реализуется — решение пользователя, для формирования ТД достаточно чертежа и 3D-модели (см. `PROGRESS.md`).

Реальная тесселяция STEP в mesh (Фаза 17, часть 5, для точного 3D-просмотра в интерфейсе):

```bash
curl -X POST http://localhost:8000/kd/step-mesh -F "step_model=@модель.step" -o модель.stl
```

Требует настроенного `PYTHONOCC_PYTHON_PATH` (см. "Требования" выше) — если не настроен или тесселяция конкретного файла не удалась (напр. сложная многокомпонентная сборка без сплошной геометрии), отвечает `404`, не `500`: это ожидаемый fallback-путь, фронтенд в этом случае показывает параметрический прокси-бокс.

## Оценка КД по НСИ (Модуль 1.2)

```bash
curl -X POST http://localhost:8000/kd/review -F "drawing=@чертёж.pdf"
```

Сверяет материал и заготовку с чертежа со справочником НСИ (metal.sqlite, создаётся автоматически при первом обращении) и классифицирует технические требования по категориям. Возвращает JSON с находками (`blocking`/`warning`/`info`) — например, "материал не найден в справочнике" или "заготовка по ГОСТ найдена, но нужный типоразмер отсутствует". Реализовано только для металлических изделий (использует metal.sqlite); сверка для аддитивных технологий не реализована.

Ответ дополнительно содержит поле `summary` (`{"text": ..., "generated_by": "llm"|"template"}`) — связное текстовое резюме находок. По умолчанию офлайн-шаблонное (`generated_by: "template"`). Если в `.env` заданы `YANDEX_GPT_API_KEY`/`YANDEX_GPT_FOLDER_ID`, резюме формируется через облачный YandexGPT API — **это единственная функция системы, требующая сети в рантайме, осознанное исключение из офлайн-требования ТЗ** (см. `dev/QUESTIONS.md` №12, `docs/ARCHITECTURE.md`). При сетевой ошибке автоматически откатывается на шаблонный текст.

Экспорт того же отчёта в PDF (дерево проверок с цветовой раскраской статусов, находки, резюме):

```bash
curl -X POST http://localhost:8000/kd/review/pdf -F "drawing=@чертёж.pdf" -o отчёт.pdf
```

## Генерация маршрутной карты — металл (Модуль 1.3, упрощённый автоподбор)

```bash
curl -X POST http://localhost:8000/kd/route-card -F "drawing=@чертёж.pdf"
```

Подбирает станки/операции по таблицам совместимости НСИ (материал + тип заготовки → допустимые станки → допустимые операции) и генерирует маршрутную карту по столбцам шаблона ГОСТ 3.1118-82. Упрощённый объём (решение пользователя): без расчёта норм времени/режимов резания и без распознавания формы детали — тип заготовки по умолчанию "прокат сортовой".

## Генерация карты печати — пластик (Модуль 1.3, упрощённый автоподбор)

```bash
curl -X POST "http://localhost:8000/print/route-card?am_technology_code=SLA&material_group_code=RESIN_STD" \
  -F "step_model=@модель.step"
```

В отличие от металла, на вход по ТЗ подаётся только STEP-модель без чертежа — технология печати (`FDM`/`SLA`/`MSLA`/`SLS`) и материал (`PETG`/`RESIN_STD`/`PA12_SLS` и т.д. — коды из `am_material_group.code`) не извлекаются из документа, а указываются явно как query-параметры. Подбирает принтер по правилам совместимости (`printer_type_material_group`) и обязательную/опциональную цепочку постобработки в правильном порядке (`material_group_pp_tooling_type`) — для фотополимерных технологий (SLA/MSLA) постобработка обязательна (мойка → дозасветка), для FDM обычно опциональна. Возвращает карту техпроцесса печати и карту постобработки по шаблонам `am_document_template`.

Операционная карта / детализация переходов и режимов резания (металл), а также параметры печати (высота слоя, время, расход материала — пластик) не реализованы — отложено на реализацию после завершения основного плана (см. `PROGRESS.md`).

## Согласование и симуляция изготовления (Модуль 2)

```bash
curl -X POST "http://localhost:8000/manufacturing/approval?decision=approved"
curl -X POST "http://localhost:8000/manufacturing/approval?decision=rejected&comment=Уточнить+разряд"

curl -X POST http://localhost:8000/manufacturing/simulate/metal -F "drawing=@чертёж.pdf"
curl -X POST "http://localhost:8000/manufacturing/simulate/print?am_technology_code=SLA&material_group_code=RESIN_STD" \
  -F "step_model=@модель.step"
```

Согласование ничего не сохраняет (нет персистентного хранилища проектов) — при `rejected` обязателен `comment`, иначе 422. Симуляция строится из того же результата автоподбора, что и маршрутная/печатная карта (не пересчитывает его заново): возвращает план из операций с долями времени (`duration_share`, в сумме дающими 15 секунд по ТЗ), кодом иконки станка/принтера для фронтенда и построчной универсальной управляющей программой (статичный шаблон, не расчёт для конкретной геометрии — см. `docs/ARCHITECTURE.md`).

## Оценка качества по фото (Модуль 3)

```bash
curl -X POST http://localhost:8000/quality/assess/metal \
  -F "drawing=@чертёж.pdf" -F "reference_photo=@эталон.jpg" -F "actual_photo=@факт.jpg"

curl -X POST "http://localhost:8000/quality/assess/print?am_technology_code=SLA&material_group_code=RESIN_STD" \
  -F "step_model=@модель.step" -F "reference_photo=@эталон.jpg" -F "actual_photo=@факт.jpg"
```

Эталон — заранее подготовленное фото качественного изделия, не рендер 3D-модели (детальная геометрия STEP в системе не строится, см. `docs/ARCHITECTURE.md`). Сравнение — по силуэту детали на фото (сегментация + нормализация + IoU), демонстрационное, не точное геометрическое, как и требует ТЗ. Три исхода: `ok`/`defective`/`inconclusive` — при недостаточной уверенности (типично при разнице ракурса съёмки) система не выдаёт вердикт произвольно. На `ok` возвращает демонстрационный план запуска в серию (себестоимость/сроки/риск/процент брака — простая эвристика, не производственный расчёт) и рекомендации по оптимизации; на `defective` — рекомендации по устранению брака.

## Просмотр БД НСИ целиком (Фаза 17, часть 5)

```bash
curl http://localhost:8000/nsi/metal/tables
curl http://localhost:8000/nsi/metal/tables/material
curl http://localhost:8000/nsi/additive/tables
```

Список таблиц (с числом строк) и содержимое конкретной таблицы (до 200 строк, с флагом `truncated`) для обеих независимых баз (`metal`/`additive`) — без привязки к какой-либо загруженной детали, в отличие от `/kd/review`. Имя таблицы всегда проверяется по белому списку реальных имён из `sqlite_master` перед подстановкой в SQL (SQLite не поддерживает параметризацию имён таблиц через placeholder) — запрос к несуществующей/произвольной строке отвечает `404`, не выполняет её как SQL.

## AI-ассистент по НСИ (Фаза 17, часть 5)

```bash
curl -X POST http://localhost:8000/assistant/chat \
  -H "Content-Type: application/json" -d '{"question": "Какие марки стали есть в базе?"}'
```

Экран "Обзор" фронтенда — окно чата, отвечающее на вопросы по НСИ/технологичности (`AssistantService`): по вопросу пользователя простым keyword-поиском (без векторного поиска/RAG) находятся релевантные записи в справочниках обеих баз НСИ (материалы, оборудование, оснастка, операции, материалы печати, классы деталей и т.д.), затем эти найденные факты передаются генератору ответа. Тот же осознанный сетевой путь и тот же принцип отката, что и LLM-резюме отчёта КД (см. предупреждение в начале файла и `QUESTIONS.md` №12): если настроен YandexGPT API — ответ формулирует LLM строго по переданным фактам (`generated_by: "llm"`), иначе или при любой ошибке — офлайн-шаблон перечисляет найденные записи текстом (`generated_by: "template"`). Источник ответа всегда возвращается и показывается в UI. Если по вопросу ничего не найдено — ассистент честно сообщает об этом, не выдумывает правдоподобный, но фиктивный ответ.

## Frontend

```bash
cd frontend
npm install
npm run dev      # dev-сервер, http://localhost:5173 (проксирует /api на backend :8000, см. vite.config.js)
npm run build    # прод-сборка в dist/
```

Реализованы экраны Модуля 1 (загрузка КД, выбор металл/пластик, результат анализа/оценки/карты), Модуля 2 (согласование с комментарием при отклонении; симуляция изготовления — 15-секундная прогресс-шкала, таймлайн операций, статичные SVG-иконки станков/принтеров, построчный вывод управляющей программы), Модуля 3 (загрузка эталонного/фактического фото, отчёт с вердиктом, ветвление на документы для серии или рекомендации по браку) и Модуля 4 (статичная иллюстративная схема цеха металл/пластик + слой IIoT — чисто фронтендовый экран, backend не требуется). Модули 1-3 требуют запущенного backend на порту 8000, Модуль 4 работает автономно.

Основной план (`PLAN.md`, Фазы 0-7) завершён.

## Офлайн-режим

Все зависимости ставятся один раз при наличии интернета (`pip install`, `npm install`). После установки приложение не обращается к сети — ни backend, ни frontend не используют CDN/облачные API в рантайме. Веса ML-моделей (когда появятся) будут храниться в `models/` и не должны требовать сети для загрузки после первого скачивания.

## Кроссплатформенность

Все пути в backend — через `pathlib.Path`, без хардкода `/` или `\`. Проверено на macOS; аналогичный набор команд должен работать на Windows без изменений (кроме активации venv — `.venv\Scripts\activate`).
