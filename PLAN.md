# PLAN.md — план разработки

Основано на `../Техническое задание.md`. Одна фаза = одна ветка `feature/phaseN-...`, вливается в `main` после Definition of Done (см. ТЗ §5.4). Порядок фаз идёт от фундамента (данные, парсинг) к пользовательскому сценарию (Модуль 1 → 2 → 3 → 4), поскольку каждый следующий модуль в бизнес-логике зависит от выхода предыдущего.

Часть решений в этом плане зависит от открытых вопросов в `QUESTIONS.md` (особенно №1 — pythonocc-core) — там, где это критично, фаза помечена как заблокированная до ответа. **Статус на 2026-08-01: все вопросы получили ответ/решение, блокировок нет.**

## Фаза 0 — Каркас проекта и ресурс-губернатор ✅ завершена (см. PROGRESS.md)

- Инициализировать структуру `dev/`: `backend/` (слои `api/services/domain/infrastructure`), `frontend/` (Vite + React 19.2), `models/` (веса, .gitignore), `docs/`.
- Настроить `pyproject.toml`/`requirements.txt` для backend, `package.json` для frontend (React 19.2, Vite 7.3, `@vitejs/plugin-react`, без TypeScript).
- Реализовать единый ресурс-губернатор (модуль в `infrastructure/`): выставляет `OMP_NUM_THREADS`, `torch.set_num_threads`, ONNX Runtime `intra_op_num_threads`/`inter_op_num_threads` по умолчанию `floor(0.4 * cpu_count)`, конфигурируемо через `.env`.
- Каркас FastAPI-приложения с воркер-пулом с ограниченным параллелизмом и очередью для тяжёлых задач (не блокировать event-loop).
- Базовый CI-скрипт локально: `pytest` (backend, пустой smoke-тест), `vite build` (frontend, пустой smoke-компонент).
- DoD: приложение поднимается на путях без хардкода `/`/`\` (через `pathlib`), CPU-губернатор покрыт тестом, который проверяет реальное количество потоков.

## Фаза 1 — БД НСИ: перенос схем в SQLite (следующая)

- Адаптировать SQL-схемы `../БД НСИ/schema/*.sql` и `../БД НСИ Аддитив/schema/*.sql` из PostgreSQL-диалекта (`SERIAL`, `JSONB`) в SQLite-совместимый (`AUTOINCREMENT`, `TEXT`/`JSON`), сохранив порядок FK-зависимостей между файлами.
- Прогнать адаптированные схемы + seed-данные на реальном локальном SQLite-файле (в отличие от оригиналов, которые не были прогнаны на живом сервере) — зафиксировать и исправить обнаруженные ошибки.
- Слой `infrastructure/db`: доступ к обеим базам (металл / аддитив) через единый интерфейс с явным выбором схемы по признаку "материал детали" (Металл/Пластик) из Модуля 1.
- DoD: обе схемы создаются и заполняются seed-данными на чистой SQLite без ошибок; тест на выборку из `equipment_type_tooling_type`/`printer_type_material_group` (ключевые таблицы совместимости) проходит.

## Фаза 2 — Модуль 1.1: парсинг входной КД

Зависит от ответа на QUESTIONS.md №1 (pythonocc-core) для 3D-части; PDF/DOC-часть не заблокирована и может идти параллельно.

- PDF/DOC чертежа и спецификации: интеграция PyMuPDF/pdfplumber (текст/векторы) и `python-docx`; заглушка/интеграция OCR (Tesseract) для сканов — за интерфейсом, чтобы модель распознавания была заменяемой.
- CV-детекция зон чертежа (основная надпись, поле ТТ, виды) — сначала оценить готовые библиотеки (по прямому указанию ТЗ п.4 "не обязательно ИИ, если есть готовая библиотека") до написания собственной модели.
- STEP-парсинг 3D-модели: реализация зависит от решения по QUESTIONS.md №1. Если pythonocc-core доступен — строить B-rep граф граней/рёбер (UV-сетки) для UV-Net; если нет — на первых итерациях переиспользовать/адаптировать `../Литература/НПО 2026/src/step_parser.py` как временное решение, явно задокументировав это как временное в `docs/ARCHITECTURE.md`.
- Извлечение метаданных цвета поверхностей (аналогично цветовой схеме из `Литература/НПО 2026/CLAUDE.md`, если применимо к входным моделям этого проекта — не считать её единственным источником истины без проверки на реальных входных STEP).
- DoD: на тестовой КД (см. QUESTIONS.md №6 — нужен fixture) извлекаются структурированные данные (виды/ТТ/надпись из чертежа, состав из спецификации, геометрия+метаданные из STEP) в единый JSON.

## Фаза 3 — Модуль 1.1 (продолжение) + 1.2: сверка с НСИ и оценка КД

- Сервис сверки извлечённых данных (материал, типоразмеры, допуски) с БД НСИ (Фаза 1).
- Скоринг корректности технических требований и доступности материала — правило-ориентированная логика в `domain/`, ML/LLM только там, где правил недостаточно (например, формулировки обратной связи).
- Генерация отчёта об оценке КД: структура отчёта, конкретные критерии оценки — уточнить по мере чтения `Литература/Белоусов ДД Конференция экономики и качесвта.docx` (QUESTIONS.md №3).
- DoD: на тестовой КД сервис выдаёт отчёт с явными находками (соответствие/несоответствие НСИ) и, при необходимости, обратной связью на этап проектирования.

## Фаза 5 — Модуль 2: согласование и симуляция изготовления

- Экран согласования комплекта ТД главным технологом (подтвердить / отклонить с комментарием → повторная генерация).
- Симуляция изготовления: универсальная заготовка NC-программы (металл) и печати (пластик), построчная имитация генерации в UI, таймер операций (15 сек по ТЗ), картинки станков (статические референсы).
- DoD: полный сценарий "согласовал → увидел симуляцию → дошёл до кнопки анализа качества" воспроизводится в UI без реального обращения к оборудованию.

## Фаза 6 — Модуль 3: оценка качества по фото

- Загрузка фото готового изделия; сравнение с 3D-моделью/её рендером для выявления явных дефектов (лишние отверстия/фаски/выступы) — по ТЗ это демонстрационное сравнение по фото, не точная геометрическая проверка.
- Ветвление: брак → рекомендации по устранению причин; норма → генерация документов для серии (план, ресурсы, сроки, оценка стоимости/рисков/процента брака — уровень детализации уточнить, см. QUESTIONS.md №8) + рекомендации по оптимизации техпроцесса.
- Генерация отчёта об оценке качества в обоих случаях.
- DoD: оба сценария (брак/норма) проходимы на тестовых фото, отчёт формируется в обоих случаях.
