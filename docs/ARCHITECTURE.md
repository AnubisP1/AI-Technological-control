# ARCHITECTURE.md

Фиксирует принятые архитектурные решения по мере их появления (обновляется по ходу фаз, не пишется один раз). Источник требований — `../../Техническое задание.md`; источник открытых вопросов и их решений — `../QUESTIONS.md`.

## Backend

- **Язык/фреймворк:** Python 3.11 + FastAPI. Причина версии 3.11 (не 3.14, как в исследовательском окружении `Литература/НПО 2026/venv`) — оставить открытым путь к `pythonocc-core`, который на 3.14 недоступен (см. `QUESTIONS.md` №1).
- **Слои:** `api` (FastAPI routes, тонкие) → `services` (сценарии/orchestration) → `domain` (бизнес-правила, ГОСТ-логика, не знает о FastAPI/БД) → `infrastructure` (БД, ML-инференс, файловый ввод-вывод, ресурс-губернатор). ML-модели подключаются в `infrastructure` за интерфейсами, объявленными в `domain` (порт/адаптер), чтобы менять реализацию (regex-парсер ↔ pythonocc-core, шаблонный текст ↔ LLM) без переписывания вызывающего кода.
- **Ресурс-губернатор** (`infrastructure/resource_governor.py`): единственное место, где выставляются `OMP_NUM_THREADS`/`MKL_NUM_THREADS`/`OPENBLAS_NUM_THREADS` и настраивается `torch`/`onnxruntime`. Вызывается первым в `main.py`, до импорта чего-либо, что может прочитать эти переменные при своём импорте.
- **Тяжёлые задачи** (STEP-парсинг, инференс) — через `infrastructure/worker_pool.run_heavy()`, `ProcessPoolExecutor` с `max_workers=1` по умолчанию (последовательное выполнение, не блокирует event loop, не создаёт межпроцессную конкуренцию за CPU поверх governor-лимита).

## Frontend

- Vite 7.3 + React 19.2, JSX (без TypeScript), обычный CSS. Стиль — Docker Desktop: тёмный сайдбар, светлая рабочая область, карточки, статус-бейджи.
- На Фазе 0 — только каркас навигации по 4 модулям ТЗ; экраны наполняются на профильных фазах (Модуль 1 → Фаза 4, Модуль 2 → Фаза 5, и т.д. — см. `../PLAN.md`).

## STEP-парсинг (Модуль 1.1, 3D-модель)

Решение по `QUESTIONS.md` №1: интерфейс `IStepParser` в `domain`, две реализации в `infrastructure`:
1. **Baseline** — адаптация regex-парсера `Литература/НПО 2026/src/step_parser.py` (без OCC, быстрый старт, покрывает цветовые метаданные и базовую геометрию AP214).
2. **Точный B-rep** (по мере необходимости для UV-Net) — `pythonocc-core` на Python 3.11.

Выбор реализации — через конфигурацию, не через дублирование вызывающего кода.

## Генерация текста (Модуль 1.2/1.3 — отчёты, формулировки)

Начинаем с шаблонной генерации (строковые шаблоны на правилах) для структурных текстов ("выявлено несоответствие пункту N"). Переход на ruT5/FRED-T5 + LoRA (архитектура из статьи Белоусова, `Литература/Белоусов ДД Конференция экономики и качесвта.docx`) — на Фазе 3, если правило-ориентированного подхода будет недостаточно для семантического сопоставления вариативных формулировок ТТ. `llama.cpp`/GGUF как алгоритм генерации отчёта не выбран — предпочтение отдано T5-семейству, поскольку оно уже профильно для этой задачи (сопоставление + генерация в одной архитектуре, а не отдельный универсальный LLM).

## OCR и анализ чертежа (Модуль 1.1)

По архитектуре из статьи Белоусова: двухэтапный OCR — детекция текстовых зон (CRAFT, CNN на VGG-16, две вероятностные карты: принадлежность пикселя символу + связность символов) → распознавание последовательности (CRNN + CTC). Целевой порог качества — CER < 2% (критично для чертежей, т.к. ошибка в символе меняет семантику требования, например допуск или диаметр). Перед реализацией собственной модели — обязательно проверить готовые библиотеки/веса под эту задачу (правило ТЗ п.4: не делать своё, если есть готовое решение).

## Контекстная фильтрация технических требований (Модуль 1.2)

По структуре из `БД НСИ/Технические требования к чертежам.pdf`: категории ТТ — материал и заменители, твёрдость/мехсвойства, термо- и химико-термическая обработка, покрытия, неуказанные предельные отклонения, допуски формы/расположения, шероховатость, технологическая последовательность, контроль/испытания, сборочные и эксплуатационные требования. Эти категории — основа для контекстной фильтрации эталонной базы НСИ при семантическом сопоставлении (сокращает пространство сравнения, как описано в статье Белоусова).

## Документы техпроцесса (Модуль 1.3)

Структура граф маршрутной карты (ГОСТ 3.1118-82) и операционной карты (ГОСТ 3.1404-86, форма 3/2а) — см. `../QUESTIONS.md` №5 для полного списка граф, найденного через веб-поиск. Заполняется в `document_template.layout_schema` схемы `БД НСИ/schema/07_documents.sql` при переносе в SQLite (Фаза 1) и используется во время генерации карт (Фаза 4).

## База данных

SQLite, адаптация PostgreSQL-схем `БД НСИ/` (металл) и `БД НСИ Аддитив/` (аддитив) — детали адаптации типов см. `../PLAN.md` Фаза 1.
