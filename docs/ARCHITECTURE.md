# ARCHITECTURE.md

Фиксирует принятые архитектурные решения по мере их появления (обновляется по ходу фаз, не пишется один раз). Источник требований — `../../Техническое задание.md`; источник открытых вопросов и их решений — `../QUESTIONS.md`.

## Backend

- **Язык/фреймворк:** Python 3.11 + FastAPI. Причина версии 3.11 (не 3.14, как в исследовательском окружении `Литература/НПО 2026/venv`) — оставить открытым путь к `pythonocc-core`, который на 3.14 недоступен (см. `QUESTIONS.md` №1).
- **Слои:** `api` (FastAPI routes, тонкие) → `services` (сценарии/orchestration) → `domain` (бизнес-правила, ГОСТ-логика, не знает о FastAPI/БД) → `infrastructure` (БД, ML-инференс, файловый ввод-вывод, ресурс-губернатор). ML-модели подключаются в `infrastructure` за интерфейсами, объявленными в `domain` (порт/адаптер), чтобы менять реализацию (regex-парсер ↔ pythonocc-core, шаблонный текст ↔ LLM) без переписывания вызывающего кода.
- **Ресурс-губернатор** (`infrastructure/resource_governor.py`): единственное место, где выставляются `OMP_NUM_THREADS`/`MKL_NUM_THREADS`/`OPENBLAS_NUM_THREADS` и настраивается `torch`/`onnxruntime`/`opencv` (`cv2.setNumThreads`, см. оговорку про GCD ниже). Вызывается первым в `main.py`, до импорта чего-либо, что может прочитать эти переменные при своём импорте.
- **Тяжёлые задачи** (STEP-парсинг, инференс) — через `infrastructure/worker_pool.run_heavy()`, `ProcessPoolExecutor` с `max_workers=1` по умолчанию (последовательное выполнение, не блокирует event loop, не создаёт межпроцессную конкуренцию за CPU поверх governor-лимита).

## Frontend

- Vite 7.3 + React 19.2, JSX (без TypeScript), обычный CSS. Стиль — Docker Desktop: тёмный сайдбар, светлая рабочая область, карточки, статус-бейджи.
- На Фазе 0 — только каркас навигации по 4 модулям ТЗ; экраны наполняются на профильных фазах (Модуль 1 → Фаза 4, Модуль 2 → Фаза 5, и т.д. — см. `../PLAN.md`).

## STEP-парсинг (Модуль 1.1, 3D-модель)

Решение по `QUESTIONS.md` №1: интерфейс `IStepParser` в `domain` (`app/domain/cad/step_parser_port.py`), реализации в `infrastructure`:
1. **Baseline, реализован** — `RegexStepParser` (`app/infrastructure/cad/regex_step_parser.py`), логика цепочки цвета адаптирована из `Литература/НПО 2026/src/step_parser.py` (без OCC, покрывает цветовые метаданные и базовую геометрию AP214). Дополнительно раскодирует STEP-escape `\X2\HHHH...\X0\` — реальные тестовые файлы от C3D Converter/АСКОН кодируют кириллицу так, а не прямым UTF-8/windows-1251, как файлы SolidWorks (под которые был написан оригинальный НПО 2026 парсер); без этого кириллические названия деталей не читались бы. Проверен на 3 реальных STEP-файлах, включая эталонную модель `Кронштейн.STEP` с известной цветовой схемой (точное совпадение).
2. **Точный B-rep** (по мере необходимости для UV-Net, не реализован) — `pythonocc-core` на Python 3.11.

Выбор реализации — через конфигурацию, не через дублирование вызывающего кода.

## Парсинг чертежа (Модуль 1.1, PDF)

`PdfDrawingParser` (`app/infrastructure/cad/pdf_drawing_parser.py`, реализует `IDrawingParser`) работает с PDF, у которых есть встроенный текстовый слой (векторный чертёж, не скан) — использует PyMuPDF. Основная надпись (ГОСТ 2.104) ищется не по абсолютным координатам (ломается на разных форматах листа A4/A3/A2/A1), а позиционно: зона штампа — эвристика по доле площади листа (нижний правый угол), значения полей ищутся относительно их текстовых меток ("Масштаб", "Формат", "Масса") — либо в той же строке справа, либо в ячейке снизу, в зависимости от того, как свёрстан конкретный штамп.

Проверено на двух реально по-разному свёрстанных чертежах (`КД для тестов/`) — потребовало нескольких итераций, т.к. первая версия давала неверные результаты: метки могут стоять и слева, и сверху от значения; наименование детали иногда переносится на несколько строк, причём строки продолжения начинаются со строчной буквы (в отличие от первой строки с заглавной); материал иногда указан одной строкой ("МАРКА ГОСТ N"), а иногда разбит на две ("Сталь МАРКА" / "ГОСТ N"). Все три случая покрыты тестами-регрессиями в `tests/test_pdf_drawing_parser.py`.

`DrawingModel.has_text_layer` явно отличает "текста нет, потому что это скан" от "текста нет, потому что поле реально пустое" — сканы без текстового слоя обрабатываются отдельным OCR-путём (см. ниже).

## Детекция видов на чертеже (Модуль 1.1)

Порт `IViewDetector` (`app/domain/cad/view_detector_port.py`), две реализации по решению пользователя (см. `QUESTIONS.md` №9 — "объедини два подхода или реализуй оба, чтобы система сама выбирала"):

1. **`VectorViewDetector`** — для векторных PDF (у всех тестовых чертежей есть векторная графика). Двухпроходная пространственная кластеризация bounding box'ов путей `page.get_drawings()`, без ML: проход 1 группирует отдельные штрихи в протокластеры фиксированным порогом (15pt); проход 2 сливает протокластеры порогом, пропорциональным их собственному размеру (0.3 × диагональ меньшего протокластера). Второй проход — результат итерации: фиксированный порог в пунктах PDF давал от 2 до 36 "видов" на разных чертежах (не масштабируется между форматами листа A3/A2), относительный порог даёт стабильные 2-6 областей на всех 7 проверенных реальных чертежах.
2. **`RasterViewDetector`** — для сканов. Рендер в растр (150 DPI) + OpenCV `connectedComponentsWithStats` после Otsu-бинаризации и дилатации — готовая библиотека вместо собственной CV/ML-модели (правило ТЗ п.4).

`AutoViewDetector` выбирает стратегию по числу векторных путей на странице (порог 20) — отделяет настоящий векторный чертёж от скана, вставленного в PDF как картинка.

Область "вид" в этом определении — самодостаточный участок листа с одной проекцией детали и её размерной сетью, а не только сам контур без аннотаций: отделить контур от размерных линий средствами одной геометрии без семантики нельзя, и для целей Модуля 1.1 (найти зоны видов) это не требуется.

## OCR для сканов (Модуль 1.1)

Изначально рассматривалась архитектура CRAFT+CRNN из статьи Белоусова (двухэтапный OCR: детекция текстовых зон CNN-детектором → распознавание последовательности CRNN+CTC, целевой CER < 2%). По решению пользователя (`QUESTIONS.md` №10 — "не принципиально, главное чтобы работало") реализован более простой путь: **`OcrDrawingParser`** на готовой библиотеке Tesseract (`pytesseract`) — соответствует правилу ТЗ п.4 (не делать своё ML-решение, если есть готовое). Обучение собственной CRAFT/CRNN-модели осталось бы отдельной исследовательской задачей вне объёма веб-приложения.

Рендер страницы в 400 DPI + бинаризация Отсу перед OCR (режим PSM 11 — разрозненный текст, подходит для страницы со scattered текстовыми фрагментами вместо связного документа) ощутимо улучшают результат по сравнению с прямым OCR необработанного цветного рендера — проверено экспериментально. Логика извлечения штампа/ТТ вынесена в общий модуль `stamp_extraction.py`, работающий с абстрактным списком строк `(x0,y0,x1,y1,text)` — и текстовый слой PDF, и результат OCR проходят один и тот же путь после получения строк текста, без дублирования позиционной эвристики между `PdfDrawingParser` и `OcrDrawingParser`.

`AutoDrawingParser` выбирает между ними по наличию текстового слоя (порог 20 символов).

**Требует установленного бинаря `tesseract` с языковым пакетом `rus`** на машине разработки/развёртывания — dev/deploy-time зависимость (macOS: `brew install tesseract-lang`; Windows: установщик tesseract-ocr с выбором Russian), соответствует офлайн-требованию ТЗ (сеть допустима на этапе разработки, всё скачанное фиксируется локально).

Качество OCR ниже, чем у текстового слоя PDF — реальное и задокументированное ограничение технологии на плотных чертёжных шрифтах, не дефект парсера: часть полей штампа на сложных сканах может остаться нераспознанной.

## Ограничение CPU-бюджета для OpenCV (кросс-компонентная заметка)

`resource_governor.configure()` вызывает `cv2.setNumThreads()` наравне с остальными движками, но **на сборках OpenCV с параллельным бэкендом GCD (Grand Central Dispatch)** — типично для `opencv-python`/`opencv-python-headless` на macOS ARM, проверяется через `cv2.getBuildInformation()` — вызов документированно не имеет эффекта: OpenCV не управляет размером пула потоков GCD. На сборках с TBB/OpenMP (типично для Linux/Windows) вызов реально ограничивает потоки. Это ограничение самого OpenCV, не баг ресурс-губернатора; учтено при подготовке кроссплатформенной сборки (Windows/Linux-дистрибутивы с TBB-сборкой OpenCV дадут полный контроль над CPU-бюджетом для растровой детекции видов и OCR, macOS ARM — частичный).

## Сверка КД с НСИ и оценка качества (Модуль 1.2)

Реализовано на Фазе 3: `app/domain/kd_review/` (модели, классификатор ТТ, чистая логика сопоставления материала/заготовки) + `app/services/kd_review_service.py` (оркестрация) + `app/infrastructure/db/sqlite_nsi_lookup.py` (доступ к metal.sqlite за портом `INsiLookup`).

**Сопоставление материала/заготовки** (`material_matching.py`) не требует точного текстового совпадения строки — формат на чертеже ("45 ГОСТ 1050-2013") систематически отличается от `grade` в справочнике ("Сталь 45"). Марка нормализуется (снятие слова "Сталь", регистронезависимо) и сравнивается отдельно от номера ГОСТ; результат — один из трёх статусов:
- `matched` — марка и ГОСТ совпали с одной и той же записью справочника;
- `partial_match` — совпало только одно из двух (напр. ГОСТ термообработки такой же, но конкретная марка в demo-НСИ отсутствует, или ГОСТ проката совпал, а нужного типоразмера/диаметра в справочнике нет) — с текстовым объяснением, что именно проверить технологу;
- `not_found` — совпадений нет вовсе.

Проверка на обоих fixture-чертежах дала три разных, содержательных результата (см. `../PROGRESS.md` Фаза 3) — это подтверждает, что логика различает случаи, а не подгоняет любой ввод под "совпало"/"не совпало".

**Классификация технических требований** (`tt_categories.py`) — по структуре из `БД НСИ/Технические требования к чертежам.pdf`: материал, термо-/химико-термическая обработка, покрытия, неуказанные предельные отклонения, допуски формы/расположения, шероховатость, технологическая последовательность, контроль/испытания, сборочные и эксплуатационные требования, справочные размеры, скругление кромок — 12 категорий, правило-ориентированный regex-классификатор, без ML. Категории и структура — из НСИ-документа, не изобретены заново. Пункт ТТ, не подпавший ни под одну категорию, не считается ошибочным — он просто нераспознан правилами и это явно отражается в отчёте (`is_recognized=False`), а не скрывается.

**Отчёт** (`KdReviewReport`/`KdReviewFinding`) — находки трёх уровней важности (`blocking`/`warning`/`info`), текст формируется шаблонно на правилах ("Материал не найден в справочнике НСИ — обратная связь конструктору: ..."), не LLM-генерацией. Соответствует общему решению по генерации текста (см. ниже): LLM подключается только когда правило-ориентированного подхода станет недостаточно.

## Генерация текста (Модуль 1.2/1.3 — отчёты, формулировки)

Начинаем с шаблонной генерации (строковые шаблоны на правилах) для структурных текстов ("выявлено несоответствие пункту N") — уже реализовано для находок Модуля 1.2 (см. выше). Переход на ruT5/FRED-T5 + LoRA (архитектура из статьи Белоусова, `Литература/Белоусов ДД Конференция экономики и качесвта.docx`) — когда правило-ориентированного подхода будет недостаточно для семантического сопоставления вариативных формулировок ТТ (напр. если сопоставление по regex-категориям начнёт давать слишком много `is_recognized=False` на реальных чертежах разных предприятий). `llama.cpp`/GGUF как алгоритм генерации отчёта не выбран — предпочтение отдано T5-семейству, поскольку оно уже профильно для этой задачи (сопоставление + генерация в одной архитектуре, а не отдельный универсальный LLM).

## Автоподбор техпроцесса и документы (Модуль 1.3)

По решению пользователя (2026-08-01) объём Фазы 4 ограничен упрощённым правило-ориентированным автоподбором — не полноценным технологическим проектированием с расчётом режимов резания. Реализовано: `app/domain/process_planning/` (модели, порт `IProcessPlanningLookup`) + `app/services/process_planning_service.py` (оркестрация) + `app/services/route_card_generator.py` (рендер карты) + `app/infrastructure/db/sqlite_process_planning_lookup.py`.

**Алгоритм автоподбора** (`ProcessPlanningService.plan()`): материал с чертежа → `material_group_id` (та же нормализация марки/ГОСТ, что и в Модуле 1.2, вынесена в общий `app/domain/material_text.py`, чтобы не дублироваться между модулями) → тип заготовки по умолчанию "прокат сортовой" (`ROLLED_BAR`) — распознавания формы детали по геометрии STEP на этой фазе нет, поэтому тип заготовки не угадывается более сложной эвристикой, которая давала бы ложное впечатление точности → пересечение `equipment_type_material_group` ∩ `equipment_type_workpiece_type` даёт допустимые типы станков → `equipment_type_operation_type` даёт допустимые операции → берётся первая доступная модель станка и вся допустимая оснастка через `operation_type_tooling_type`. Порядок операций в итоговой карте (черновая → чистовая → фрезерная → сверлильная → шлифовальная → контрольная) — технологически осмысленное решение в коде сервиса, а не порядок строк в БД (таблицы совместимости не хранят приоритет).

Проверка на fixture 1 (вал, сталь 45) дала содержательный результат: подобраны токарные и шлифовальная операции с конкретными станками и оснасткой, но **не** сверлильная — потому что demo-НСИ связывает сверлильный станок только с заготовками "поковка"/"отливка", не с "прокат сортовой". Это не баг: сервис честно отражает то, что разрешено таблицами совместимости, а не выдумывает операцию сверх правил.

**Документы**: структура граф маршрутной карты (ГОСТ 3.1118-82) и операционной карты (ГОСТ 3.1404-86, форма 3/2а) — см. `../QUESTIONS.md` №5. `RouteCardGenerator` строит карту по `document_template.layout_schema` (JSON в БД), а не хардкодит столбцы в коде — карта переживает правки состава граф. Графы, которые автоподбор не рассчитывает (Тпз, Тшт, разряд работ, цех/участок), в карте остаются пустыми — не заполняются выдуманными значениями. Операционная карта (детализация по переходам с режимами резания t/S/V/n) не реализована на этой фазе — требует расчёта режимов резания, вне объёма упрощённого автоподбора.

## База данных

SQLite. Адаптированные схемы лежат в `backend/app/infrastructure/db/schema_sqlite/{metal,additive}/` (metal = `БД НСИ/`, additive = `БД НСИ Аддитив/`), загрузчик — `backend/app/infrastructure/db/nsi_db.py` (`build_database()`/`connect()`). Обе схемы независимы (без FK друг на друга), выбор — по признаку "материал детали" (Металл → metal, Пластик → additive) из Модуля 1.

Ключевые отличия от PostgreSQL-оригиналов: `SERIAL` → `INTEGER PRIMARY KEY AUTOINCREMENT`, `JSONB` → `TEXT`, `now()` → `datetime('now')`, `COMMENT ON` → обычные SQL-комментарии. Одно структурное изменение: `БД НСИ/06_process.sql` в оригинале добавлял FK к таблице `workpiece` постфактум через `ALTER TABLE ADD CONSTRAINT` (SQLite это не поддерживает) — в SQLite-версии FK на `part(id)` объявлен сразу в `CREATE TABLE workpiece` (файл 04); работает, потому что SQLite не проверяет существование целевой таблицы FK на момент `CREATE TABLE`, только при последующих операциях с данными.

Обе схемы прогнаны на живом SQLite и покрыты тестами (`backend/tests/test_nsi_db.py`) — это первый реальный прогон этих схем на каком-либо сервере БД (оригинальные README отмечали, что схемы были проверены только структурно). При прогоне обнаружена и исправлена ошибка порядка seed-файлов в additive-схеме (`seed_application_rules.sql` зависит от `seed_data.sql`, но шёл раньше по алфавиту) — порядок теперь задаётся явно в `nsi_db.py`, а не через сортировку по имени файла.
