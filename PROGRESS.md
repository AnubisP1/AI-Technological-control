## Фаза 1 — БД НСИ: перенос схем в SQLite

**Статус: завершена.** Дата: 2026-08-01.

### Сделано

- Все 17 SQL-файлов обеих схем (`БД НСИ/` — 7 schema + 1 seed, `БД НСИ Аддитив/` — 8 schema + 2 seed) прочитаны полностью и адаптированы под SQLite в `backend/app/infrastructure/db/schema_sqlite/{metal,additive}/`.
- Синтаксические замены: `SERIAL` → `INTEGER PRIMARY KEY AUTOINCREMENT`, `JSONB` → `TEXT`, `TIMESTAMP NOT NULL DEFAULT now()` → `TEXT NOT NULL DEFAULT (datetime('now'))`, `TRUE`/`FALSE` → `1`/`0`, `COMMENT ON TABLE/COLUMN` перенесены в обычные SQL-комментарии над определением.
- **Устранена структурная проблема, которую SQLite не терпит, а PostgreSQL допускал:** `БД НСИ/schema/06_process.sql` в оригинале добавляет FK к уже созданной таблице `workpiece` через `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` (workpiece создаётся в файле 04, а `part`, на которую он ссылается, — в файле 06). SQLite не поддерживает добавление FK к существующей таблице. Решение: FK на `part(id)` объявлен сразу в `CREATE TABLE workpiece` (файл 04 SQLite-версии) — работает, потому что SQLite не проверяет существование таблицы, на которую ссылается FK, в момент `CREATE TABLE` (только при последующих `INSERT`/`UPDATE` с включённым `PRAGMA foreign_keys`), так что порядок файлов (part позже) не мешает.
- `backend/app/infrastructure/db/nsi_db.py`: `build_database()` создаёт SQLite-файл, применяет схему и seed по явно заданному порядку файлов (важно: `seed_application_rules.sql` в аддитивной схеме зависит от `seed_data.sql`, а не наоборот — при алфавитной сортировке ловилась `FOREIGN KEY constraint failed`, порядок исправлен на явный список, а не glob-сортировку по имени); `connect()` открывает соединение с `PRAGMA foreign_keys = ON`.
- **Обе схемы реально прогнаны на живом SQLite-файле** — впервые за всё время существования этих схем (README обеих исходных папок прямо указывал, что они не были прогнаны ни на PostgreSQL, ни где-либо ещё). Metal: 32 таблицы, additive: 34 таблицы, обе строятся из чистого файла за ~20 мс.
- Тесты (`pytest`, 6 новых тестов в `test_nsi_db.py`): обе схемы+seed загружаются без ошибок; ключевая compatibility-таблица `equipment_type_tooling_type` даёт непустой результат для реального типа станка из seed; FK `workpiece.part_id` реально проверяется (валидная вставка проходит, невалидный `part_id` вызывает `IntegrityError`); колонка `am_part.part_application_class_id`, добавленная через `ALTER TABLE ADD COLUMN` в 08-м файле, реально доступна; `application_material_recommendation` содержит посеянные строки; сборка без seed даёт пустые, но валидные таблицы. **Все 10 тестов backend (3 из Фазы 0 + 6 из Фазы 1 + 1 ранее) проходят.**
- `layout_schema` шаблонов `document_template` (metal) дополнен полным составом граф маршрутной/операционной карты по найденной структуре ГОСТ 3.1118-82/3.1404-86 (было — сокращённый список из оригинального seed, стало — полный: номер операции/перехода, содержание, оборудование, оснастка, режимы t/S/V/n, разряд работы, нормы времени То/Тв/Тшт/Тпз).

## Фаза 2 — Модуль 1.1: парсинг входной КД

**Статус: завершена.** Дата: 2026-08-01.

### Сделано

- **Доменный слой** (`app/domain/cad/`): `StepModel`/`BoundingBox`/`FaceColour`, `DrawingModel`/`TitleBlockFields`/`TechnicalRequirement`, `KdAnalysisResult`, порты `IStepParser`/`IDrawingParser` (Protocol) — реализации подключаются из `infrastructure`, домен о них не знает.
- **`RegexStepParser`** (`app/infrastructure/cad/regex_step_parser.py`) — baseline-реализация `IStepParser` по решению из QUESTIONS.md №1. Логика цепочки цвета (`STYLED_ITEM → ... → COLOUR_RGB`) взята за основу из `Литература/НПО 2026/src/step_parser.py`, но переписана под контракт этого проекта и дополнена раскодированием STEP-escape `\X2\HHHH...\X0\` — реальные тестовые STEP-файлы от C3D Converter/АСКОН кодируют кириллицу именно так, а не прямым UTF-8/windows-1251, как файлы SolidWorks, под которые был написан оригинальный парсер. Без этой доработки кириллические названия деталей не читались бы вовсе.
- **Валидация парсера на 3 реальных STEP-файлах**, а не только на синтетике:
  - `Кронштейн.STEP` (эталон из НПО 2026, известные значения) — 20 граней, цветовая схема точно совпала (9 фасок синих, 6 плоскостей голубых, 4 галтели зелёных, 1 отверстие красное).
  - Два fixture-файла из `КД для тестов/` (вал, шестерня) — оба успешно распарсены, bounding box вала по оси X (707.488 мм) совпал с размером 707±1 с чертежа этой же детали (перекрёстная проверка между STEP и PDF одного изделия).
- **`PdfDrawingParser`** (`app/infrastructure/cad/pdf_drawing_parser.py`) — извлечение основной надписи (ГОСТ 2.104) и технических требований из PDF с текстовым слоем через PyMuPDF. Поля штампа ищутся позиционно относительно текстовых меток ("Масштаб", "Формат", "Масса"), а не по хардкод-координатам — устойчиво к разным форматам листа.
  - **Существенная итерация на реальных данных**: первая версия давала неверные значения на обоих fixture (перепутанные поля, значения-лейблы вместо значений, часть текста пропущена) — оказалось, что метки в штампе могут стоять и слева, и сверху от значения в зависимости от графы, наименование детали может переноситься на несколько строк с продолжением со строчной буквы, а материал иногда разбит на две строки ("Сталь МАРКА" / "ГОСТ N") вместо одной. Все случаи выявлены и исправлены именно потому, что тестировалось на двух по-разному сверстанных реальных чертежах, а не на одном.
  - Технические требования нумеруются последовательно с проверкой (не даёт ложных срабатываний на даты вида "24.02.2023" или допуски вида "0.025", которые синтаксически похожи на "число.текст").
  - `has_text_layer` явно сигнализирует отсутствие текстового слоя (скан) — не подменяется тихой выдачей пустых полей, которая была бы неотличима от чертежа, где поля реально отсутствуют.
- **`KdAnalysisService`** (`app/services/`) — оркестрирует парсер чертежа, детектор видов и парсер STEP-модели через `worker_pool.run_heavy`, чтобы разбор не блокировал event loop.
- **`POST /kd/analyze`** — эндпоинт загрузки чертежа (опционально) и STEP-модели (опционально, для пластиковых изделий по ТЗ — только STEP без чертежа), возвращает структурированный JSON (включая детекцию видов).
- Тесты (`pytest`, 16 новых на первом проходе): 6 для STEP-парсера, 6 для PDF-парсера, 3 для эндпоинта, 1 нагрузочный CPU-тест.
- Закрыт отложенный пункт DoD Фазы 0: нагрузочный тест с реальной вычислительной нагрузкой (`test_cpu_budget_load.py`) — подтверждает, что парсинг не порождает дополнительных потоков сверх бюджета ресурс-губернатора.

### Продолжение Фазы 2 (по решениям пользователя от 2026-08-01)

Пользователь принял три решения: (1) отменить парсинг спецификации — не нужен для формирования ТД; (2) реализовать детекцию видов на чертеже, используя дополнительные чертежи из `КД для тестов/Детали из металла/Архив/` для тестирования; (3) для OCR сканов не обязательно следовать архитектуре CRAFT+CRNN из статьи Белоусова — важен результат, а не конкретный метод.

- **Детекция видов на чертеже** (`app/domain/cad/view_detection_model.py`, `view_detector_port.py`) — единый порт `IViewDetector`, две реализации:
  - **`VectorViewDetector`** — двухпроходная пространственная кластеризация bounding box'ов векторных путей PDF (`page.get_drawings()`), без внешних ML-зависимостей. Проход 1: плотная кластеризация штрихов в протокластеры (фиксированный порог 15pt). Проход 2: укрупнение протокластеров порогом, пропорциональным их собственному размеру (0.3 × диагональ меньшего) — это ключевое решение после итерации: фиксированный порог в пунктах PDF давал от 2 до 36 "видов" в зависимости от чертежа (не масштабируется между форматами листа A3/A2), относительный порог даёт стабильные 2-6 областей на всех 7 проверенных реальных чертежах (2 основных fixture + 5 из `Архив/`, включая дополнительные, не участвовавшие в калибровке алгоритма — тест на переобучение порогов).
  - **`RasterViewDetector`** — рендер страницы в растр + OpenCV (`connectedComponentsWithStats` после Otsu-бинаризации и дилатации) для сканов. Готовая библиотека вместо своей CV-модели (правило ТЗ п.4).
  - **`AutoViewDetector`** — выбирает стратегию по числу векторных путей на странице (≥20 → вектор, иначе растр).
- **OCR для сканов** — `OcrDrawingParser` на Tesseract (`pytesseract`), не CRAFT+CRNN. Требует установленного бинаря `tesseract` с языковым пакетом `rus` (dev-time зависимость: `brew install tesseract-lang` на macOS). Рендер в 400 DPI + бинаризация Отсу перед OCR (PSM 11 — разрозненный текст) ощутимо улучшают результат по сравнению с прямым OCR необработанного цветного рендера — проверено экспериментально на синтетическом "скане" реального fixture.
  - **Рефакторинг для переиспользования**: логика извлечения штампа/ТТ вынесена из `PdfDrawingParser` в отдельный модуль `stamp_extraction.py`, работающий с абстрактным списком строк `(x0,y0,x1,y1,text)` — теперь и текстовый слой PDF, и результат OCR проходят один и тот же путь извлечения после получения строк, без дублирования позиционной эвристики.
  - **`AutoDrawingParser`** — выбирает PDF-текст или OCR по наличию текстового слоя (≥20 символов).
  - Качество OCR ниже текстового слоя (реальное ограничение технологии на плотных чертежах, не дефект парсера) — задокументировано, тесты проверяют, что конвейер работает end-to-end, а не точное совпадение полей.
- **Побочная находка про CPU-бюджет**: `cv2.setNumThreads()` не имеет эффекта на сборках OpenCV с параллельным бэкендом GCD (типично для macOS ARM, подтверждено через `cv2.getBuildInformation()`) — документированное ограничение самого OpenCV, не баг ресурс-губернатора. Governor всё равно вызывает `cv2.setNumThreads()` (реально работает на сборках с TBB/OpenMP — Linux/Windows), тест проверяет применимый на любой платформе инвариант, а не факт ограничения.
- Тесты: +9 (детекция видов на 2 доп. архивных чертежах + границы регионов + raster-путь на синтетическом скане + автовыбор для обоих путей + OCR end-to-end + auto-parser routing), +1 обновлённый (ресурс-губернатор), обновлён тест эндпоинта под новое поле `view_detection`. **Все 36 backend-тестов проходят.**

## Фаза 3 — Модуль 1.2: сверка с НСИ и оценка КД

**Статус: завершена.** Дата: 2026-08-01.

### Сделано

- **Доменный слой** (`app/domain/kd_review/`): `MaterialCheck`/`BlankCheck`/`TechnicalRequirementCheck`/`KdReviewFinding`/`KdReviewReport` с трёхуровневым `MatchStatus` (matched/partial_match/not_found) — статус `not_found` явный, не подменяется молчаливой выдачей "первого похожего" результата.
- **`material_matching.py`** — сопоставление строки материала/заготовки с чертежа со справочником НСИ через нормализацию (снятие слова "Сталь", регистронезависимое сравнение кода марки) и отдельное сравнение номера ГОСТ. Формат на чертеже не совпадает буква-в-букву с `grade` в БД ("45 ГОСТ 1050-2013" на чертеже vs "Сталь 45" в справочнике) — точное текстовое совпадение было бы неработоспособно, поэтому марка и ГОСТ сравниваются раздельно, и любое частичное совпадение помечается как `partial_match` с объяснением, а не как ложный `matched`.
- **`tt_categories.py`** — классификатор из 12 категорий технических требований (материал, термо/химико-термическая обработка, покрытия, неуказанные допуски, допуски формы/расположения, шероховатость, технологическая последовательность, контроль/испытания, сборочные и эксплуатационные требования, справочные размеры, скругление кромок) — правило-ориентированный (regex), без ML, категории и структура взяты из `БД НСИ/Технические требования к чертежам.pdf` (не изобретены заново). Паттерны неоднократно скорректированы по реальным формулировкам из fixture-чертежей (напр. "притупить" стоит после "кромки", а не перед).
- **`KdReviewService`** (`app/services/`) — оркестрирует сверку материала, заготовки и классификацию всех пунктов ТТ, формирует список находок (`KdReviewFinding`) трёх уровней важности (`blocking`/`warning`/`info`). Текст находок — шаблонная генерация на правилах, не LLM (соответствует решению из `docs/ARCHITECTURE.md`: LLM подключается только если правил станет недостаточно).
- **`SqliteNsiLookup`** (`app/infrastructure/db/`) — реализация порта `INsiLookup` поверх metal.sqlite (из Фазы 1); ГОСТ заготовки в текущей схеме встроен в поле `designation`, а не хранится отдельно — извлекается регэкспом на уровне infrastructure, а не считается недостатком domain-модели.
- **`POST /kd/review`** — эндпоинт: загружает чертёж, разбирает через уже существующий `AutoDrawingParser`, лениво инициализирует `data/metal.sqlite`, если файла ещё нет (сверка не требует ручного шага перед первым запуском backend), возвращает отчёт.
- **Проверка на обоих реальных fixture-чертежах** дала три содержательно разных исхода, подтверждающих, что логика не подгоняет результат под ожидание:

## Фаза 6 — Модуль 3: оценка качества по фото

**Статус: завершена.** Дата: 2026-08-01. Ключевой архитектурный вопрос этой фазы — чем сравнивать фото изготовленного изделия, если система не строит настоящую 3D-геометрию STEP (см. QUESTIONS.md №1, №11): решение — эталонное фото/изображение детали, а не честный рендер модели, что прямо разрешено формулировкой ТЗ "как будет проще".

### Сделано

- **`app/domain/quality_control/`** — `quality_model.py` (`QualityVerdict`: ok/defective/inconclusive, `PhotoComparisonResult`), `photo_comparator_port.py` (`IPhotoComparator`), `serial_production_model.py` (`SerialProductionPlan`, `ProcessOptimizationSuggestion`, `DefectRemediationRecommendation`, `QualityReport`).
- **`OpenCvPhotoComparator`** (`app/infrastructure/quality_control/opencv_photo_comparator.py`) — сравнение силуэта детали на фото классическим CV (Otsu-сегментация крупнейшего контура → нормализация по площади и центру масс, не по bounding box → перебор поворота 0..345° с шагом 15° → IoU после выравнивания). Без ML/нейросети — по правилу ТЗ п.4 и по прямой формулировке сценария ("не сравниваем точно по миллиметрам, достаточно просто сравнить по фото").
- **Калибровка порогов на реальных тестовых фото** (4 фото одной физической пластиковой детали, `КД для тестов/Пластиковые детали/.../*.jpeg`, разные ракурсы): одинаковый ракурс даёт IoU ~0.90-0.97, разные ракурсы одной детали — ~0.63-0.71. Итоговые пороги: IoU ≥0.80 → `ok`, <0.55 → `defective`, между ними — `inconclusive` (не выдаём вердикт при недостаточной уверенности — разница ракурса на этих реальных фото не должна быть принята за брак).
- **Важная находка при прототипировании**: нормализация по bounding box (а не по площади силуэта) "прятала" синтетический дефект — расширение bbox из-за лишнего выступа автоматически перемасштабировало всю деталь, и IoU почти не менялся. Переход на нормализацию по площади (эквивалентный диаметр через `sqrt(area/π)`) исправил это.
- **Решение по глубине детализации находок** (см. QUESTIONS.md №11): отчёт даёт только общий вердикт и метрику схожести, не пытается локализовать конкретный тип дефекта (отверстие/фаска/выступ) — прототипирование показало, что размер наибольшего "лишнего" пятна от обычного шума фото (~1.2% площади) сопоставим с размером синтетического тестового дефекта (~1.8%), точная классификация была бы избыточной точностью, которую метод не может подтвердить.
- **`QualityControlService`** (`app/services/quality_control_service.py`) — оркестрация 3.1→3.2: на `ok` строит `SerialProductionPlan` (демонстрационная эвристика от числа операций автоподбора + фиксированные коэффициенты риска от числа warnings, см. QUESTIONS.md №8) и `ProcessOptimizationSuggestion`; на `defective` — `DefectRemediationRecommendation`; на `inconclusive` — только отчёт, без ветвления в документы (не привязываем демонстрационные документы к неуверенному результату).
- **Эндпоинты** `POST /quality/assess/metal` и `POST /quality/assess/print` — переиспользуют автоподбор техпроцесса (Модуль 1.3) и сборку `SimulationPlan` (Модуль 2, Фаза 5) для построения серийной эвристики, не дублируют эту логику.
- **Побочная находка/исправление**: `run_heavy()` (`app/infrastructure/worker_pool.py`) при вызове с kwargs использовал лямбду, которая не пиклится через `ProcessPoolExecutor` — падало только при первом реальном вызове с kwargs через межпроцессный воркер-пул (все прежние вызовы использовали только позиционные аргументы). ## Фаза 21 — веб-поиск для AI-ассистента, когда НСИ не даёт ответа

**Статус: завершена.** Дата: 2026-08-04. По прямому запросу пользователя: "ответы на вопросы которые пользователь задает ассистенту можешь искать в интернете через polza если нет информации в БД НСИ".

Если `matches` непустой, веб-поиск не вызывается вовсе, даже если основной LLM-путь недоступен — не подменяет уже найденные реальные факты внешним источником.
- **`_build_web_search_responder()`** в `routes.py` — использует тот же `POLZA_API_KEY`, первую модель из `POLZA_MODELS` (отдельная настройка модели не заводилась — по решению пользователя).

  **Найденная и исправленная в этой же фазе регрессия (обнаружена на живом сервере, не тестами)**: изначально веб-поиск был помещён внутрь `except` основного `chat_responder` — но при пустых `matches` обычный `chat_responder` (антигаллюцинационный промпт, ограниченный переданными фактами) УСПЕШНО возвращает "не найдено в НСИ" — это не исключение, поэтому код никогда не доходил до ветки веб-поиска. Реальный вызов ("Сколько лет Эйфелевой башне?") подтвердил: ответ приходил от обычного Polza-провайдера ("не найдено"), не от веб-поиска. ### Сделано

- **Извлечение реальной топологии STEP через pythonocc-core** — новый автономный скрипт `occ_feature_extract_script.py` (по образцу `occ_step_to_stl_script.py`) обходит `TopExp_Explorer` по граням, классифицирует каждую через `BRepAdaptor_Surface`/`GeomAbs_Plane`/`GeomAbs_Cylinder`. Критерий "сквозное отверстие vs галтель-скругление" для цилиндрических граней — угловой охват параметра U (полный оборот ~2π = отверстие, ~π/2 = скругление прямого угла) — эмпирически подтверждён на реальном fixture `Литература/НПО 2026/Кронштейн.STEP` (20 граней: 1 отверстие Ø25 с полным углом против 4 галтелей R10 с углом ~π/2 каждая). `step_feature_extractor.py` — Python-обёртка (subprocess, тот же паттерн, что и у тесселяции).
- **Классификатор фич** (`topology_feature_classifier.py`, `PartTopology` → `PartFeatureSet`) — плоские грани с нормалью вдоль Z → обрабатываемые facing-грани; полнооборотные цилиндры разумного диаметра относительно габарита → отверстия; остальное — не покрыто v1, попадает в `unrecognized_face_count`, но НЕ блокирует поддержку детали целиком (фаски/галтели — обычная конструктивная деталь, не признак непризматичности).
  **Найденная и исправленная в процессе ошибка классификации (обнаружена на реальном fixture "Вал", не выдумана заранее)**: первая версия критерия "разумный диаметр отверстия" сравнивала диаметр цилиндра с диагональю всего габарита — на валу (переменное сечение, ступени Ø45-65мм при поперечном габарите 65мм) это давало 9 ложных "отверстий" вместо честного "это не подходящая деталь". Пользователь подсказал первопричину: "Вал делается не фрезерованием, а точением — деталь вращения". Добавлена явная проверка "тело вращения" ДО попытки распознать отверстия: доля полнооборотных цилиндров с общей осью среди всех цилиндрических граней (порог 0.4 доли + минимум 3 соосных цилиндра) — 0.60 у реального вала против 0.20 у кронштейна и 0.04 у шестерни, разделяет с большим запасом на всех трёх reference fixture проекта. Деталь-тело-вращения получает `is_supported=False` и честное предупреждение, не траекторию по несуществующей логике.
- **Генератор траекторий** (`toolpath_generator_service.py`) — режимы резания считаются по формуле `V=Cv/(T^m·t^xv·S^yv)·Kv` (те же коэффициенты НСИ, что уже использовал `CuttingModeCalculator` из Фазы 17), но обороты шпинделя — по диаметру РЕЖУЩЕГО ИНСТРУМЕНТА (`n=1000V/(πD)`), не диаметру заготовки — существующий калькулятор физически рассчитан на точение/сверление круглого прутка, для фрезерования плиты диаметра заготовки не существует в принципе. Инструмент подбирается из реально засеянных `tooling` НСИ (новый метод порта `find_tooling_by_type_code`) по ближайшему подходящему диаметру. Facing — зигзаг по bounding box грани; отверстие — прямое сверление (с циклом вывода стружки при глубине >3×диаметра — реальное технологическое правило) СВЕРЛОМ, если в НСИ есть инструмент подходящего диаметра, иначе — круговая интерполяция концевой фрезой (полигональная аппроксимация окружности, 32 сегмента; честно помечена в `source_note` как fallback-стратегия из-за отсутствия сверла нужного диаметра в справочнике — не выдана за то же самое, что настоящее сверление). Постпроцессор — Fanuc-подобный G-code (G0/G1, M03/M05), не Heidenhain (UST-1 — референс сложности, не целевой диалект, согласовано с пользователем).
  **Найденный попутно пробел в НСИ, закрыт по ходу**: `feed_reference` (типовая подача/глубина резания) была засеяна только для стальных `material_group` — демо-fixture (Кронштейн) алюминиевый, без данных для `ALUM` генератор не мог посчитать ни одной операции. Добавлены реальные строки для `ALUM` в `seed_cutting_modes.sql` (тот же источник — Справочник технолога-машиностроителя Косилова/Мещерякова, т.2, табл. 35/25 — содержит отдельные значения и для алюминиевых сплавов, не только сталей).
- **Voxel-симуляция реального съёма материала** (`material_removal_simulator.py`) — по прямому запросу пользователя ("визуализация прохода фрезы по заготовке... в ускоренном темпе"): заготовка — numpy bool-массив (адаптивное разрешение, ≤120 вокселей на большую ось, бюджет CPU/памяти), каждое линейное движение инструмента растеризует "вырезание" вокселей в радиусе `tool_diameter_mm/2` вдоль отрезка. Результат — компактный sparse-список событий "воксель X,Y,Z удалён на шаге N" (не полный покадровый вывод) — 0.07с на реальном fixture (35764 события, 244800 вокселей сетки), укладывается в CPU-бюджет с большим запасом.
- **Новый эндпоинт `POST /manufacturing/toolpath/metal`** — принимает STEP+чертёж, весь тяжёлый путь (топология → классификация → тулпас → voxel-симуляция) выполняется одной функцией `run_toolpath_pipeline` через `run_heavy` (один воркер `ProcessPoolExecutor`, как и остальные тяжёлые операции проекта). JSON-ответ включает `start_step`/`end_step` на операцию (вычисляются как зеркало того же правила инкремента шага, что использует симулятор) — фронтенд подсвечивает активную операцию синхронно с прогрессом voxel-анимации без передачи полного списка `moves`. Старый `/manufacturing/simulate/metal` (без геометрии) помечен как legacy-путь, не удалён — работает, если по какой-то причине STEP недоступен.
- **Фронтенд**: `WorkflowInput` для металла теперь несёт обязательный `stepModel` (раньше опциональный на "Анализ детали", по решению пользователя стал обязательным — без геометрии реальный тулпас не строится). Новый `ToolpathViewer.tsx` (R3F) — воксели рендерятся как один `InstancedMesh` (не пересоздаётся на каждый кадр — только матрицы трансформации через `setMatrixAt`), скрытие вокселя = масштаб в 0. `ProductionPage.tsx` переписан: реальный путь (`ToolpathSimulation`, показывает `ToolpathViewer`+прогресс+G-code активной операции) для металла с STEP, легаси-путь (`LegacySimulation`, старая логика без изменений) остаётся для пластика.
  **Найденный и исправленный визуальный баг камеры (обнаружен реальной Playwright-проверкой на живом GPU, не в тестах)**: фиксированная изометрическая позиция камеры `[3,2,3]` (тот же паттерн, что уже в `PartViewer.tsx`) хороша для кубовидных деталей, но для сильно вытянутой/плоской заготовки (реальный Кронштейн — 106×26×60мм) давала ракурс, где силуэт схлопывался в нечитаемый узкий "шеврон" вместо узнаваемой плиты. Первая попытка исправления (вес компоненты направления обратно пропорционален протяжённости оси, линейно) оказалась хуже — камера уходила строго вдоль самой длинной оси, деталь становилась плоским "анфас"-прямоугольником без объёма. Финальное решение — компонента направления камеры растёт с протяжённостью детали по оси (не наоборот), через квадратный корень отношения (мягкая, не резкая коррекция) — визуально подтверждено (два независимых Playwright-прогона на реальном GPU) как читаемый объёмный силуэт плиты.

### Доработка визуализации по обратной связи пользователя (та же сессия, сразу после первой версии)

Пользователь посмотрел первую версию вживую на реальной детали "Шестерня" (сложная геометрия — коническая передача с зубом, v1-классификатор распознаёт только центральное отверстие и торцевые грани, не зубья) и указал на реальную проблему: симуляция дошла до "шаг 79 из 79" (100%), но сцена показывала пустой пол — весь материал заготовки был вычтен, а конечный результат никак не напоминал шестерню, потому что voxel-симулятор только вычитал материал по вычисленной траектории, не имея отдельного эталона "как должна выглядеть готовая деталь" для сравнения. Пользователь прямо сформулировал требуемое поведение: "должно отображать как фреза убирает постепенно материал и из заготовки в процессе изготовления появляется модель детали", с конкретной цветовой схемой — заготовка полупрозрачным голубым, целевая модель зелёным, инструмент красным.

- **Три слоя геометрии в одном мировом пространстве координат** (`ToolpathViewer.tsx` переписан): `StockVoxels` — та же voxel-логика, что и раньше, но теперь полупрозрачный голубой материал (`transparent opacity={0.22}`), не непрозрачный серый; `TargetModel` — НОВЫЙ слой, зелёная целевая модель, полученная переиспользованием уже существующего пайплайна реальной тесселяции STEP (`fetchStepMesh`/`step_mesh_exporter.py`/pythonocc-core — тот же самый путь, что `PartViewer.tsx` уже использует на экране "Анализ детали", не новая зависимость и не выдуманный контур); `ToolCursor` — НОВЫЙ слой, красный цилиндр, интерполирующий положение по `moves` активной операции синхронно с `currentStep`.
- **Backend**: `ToolpathOperation.moves` (реальные координаты движения инструмента, раньше не сериализовались — фронтенду хватало только текстового `gcode_lines`) добавлены в JSON-ответ `/manufacturing/toolpath/metal` — небольшое увеличение payload (десятки точек на операцию), нужны фронтенду для анимации положения фрезы.
- **Единый источник времени анимации**: `currentStep` поднят в родительский `Scene`-компонент (`useAnimationStep`) вместо независимого таймера внутри `StockVoxels` — `StockVoxels` и `ToolCursor` теперь гарантированно синхронны (двигаются относительно одного и того же шага), не два рассинхронизированных счётчика.
- **`Bounds fit` применяется один раз ко всей сцене** (заготовка+цель+инструмент вместе как одна группа `<Center>`), не по отдельности к каждому источнику геометрии — все три уже в одном мировом пространстве координат от backend (мм), раздельное центрирование "разъехало" бы их относительно друг друга.

## Открытые архитектурные решения, принятые в ходе работы

См. `QUESTIONS.md` — все пункты закрыты решениями (не пользователем поштучно, а с явным делегированием "поступай как считаешь нужным" по вопросам 1, 2, 7, 8). Кратко:
- Backend: Python 3.11 + FastAPI (не Python 3.14, чтобы оставить путь к `pythonocc-core` открытым).
- STEP-парсинг: через интерфейс `IStepParser`, первая реализация — адаптация regex-парсера из `Литература/НПО 2026/src/step_parser.py`, вторая (по необходимости) — `pythonocc-core`.
- LLM: без резервирования весов заранее; текст отчётов/карт на первых фазах — шаблонный, ruT5/FRED-T5+LoRA (из статьи Белоусова) подключается на Фазе 3, если правил недостаточно.
- Метрики Модуля 3.2 (риски/брак/стоимость) — демонстрационная эвристика с явной пометкой в UI, не производственный расчёт.
- Спецификация (БОМ) — отменена явным решением пользователя, не входит в объём проекта.
- Детекция видов на чертеже — две реализации (векторная кластеризация + растровая CV-сегментация) за одним портом с автовыбором, а не единственный универсальный алгоритм.
- OCR сканов — готовая библиотека Tesseract вместо собственной CRAFT+CRNN-архитектуры, по явному решению пользователя ("не принципиально, главное чтобы работало").
