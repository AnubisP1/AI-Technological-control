## Фаза 0 — Каркас проекта и ресурс-губернатор

**Статус: завершена.** Дата: 2026-08-01.

### Сделано

- Backend: FastAPI-каркас на Python 3.11 (`backend/app`), слои `api/services/domain/infrastructure` созданы (services/domain пока пустые — наполняются с Фазы 1+).
- Ресурс-губернатор (`backend/app/infrastructure/resource_governor.py`): единая настройка `OMP_NUM_THREADS`/`MKL_NUM_THREADS`/`OPENBLAS_NUM_THREADS`, готовность к `torch.set_num_threads` и ONNX Runtime `SessionOptions`. По умолчанию `floor(0.4 * cpu_count)`, конфигурируется через `.env` (`CPU_BUDGET_FRACTION`). Вызывается в `main.py` до импорта FastAPI/остального кода.
- Worker pool (`backend/app/infrastructure/worker_pool.py`): `ProcessPoolExecutor`-обёртка `run_heavy()` для тяжёлых задач вне event loop, по умолчанию `max_workers=1` (последовательное выполнение, чтобы не создавать конкуренцию за CPU поверх уже ограниченных внутри задачи потоков).
- Конфиг через `pydantic-settings` + `.env` (`backend/.env.example`), без секретов в коде.
- Логирование: единая точка `configure_logging()`.
- `/health`-эндпоинт возвращает фактически применённый CPU-бюджет — можно проверить лимит без обращения к внутренним модулям.
- Тесты (`pytest`, 3 теста): ресурс-губернатор считает потоки корректно (`floor`, минимум 1), `OMP_NUM_THREADS` реально выставляется, `/health` отвечает и бюджет ≤ общего числа ядер. **Все 3 теста проходят.**
- Frontend: Vite 7.3.6 + React 19.2 (`^19.2.0`), JSX без TypeScript (только `@types/react`/`@types/react-dom` для IDE), обычный CSS (`index.css`, `App.css`, заготовка `auth.css`). Каркас: боковая навигация (4 модуля из ТЗ), светлая тема, карточка, статус-бейдж — в духе Docker Desktop.
- `npm run build` — собирается без ошибок (`dist/` генерируется).
- Дев-сервер проверен вживую через Playwright (headless Chromium, временно установлен и удалён — не входит в постоянные зависимости): страница рендерится, навигация между модулями работает, ошибок в консоли браузера нет. Скриншоты не сохранены в репозитории (не являются частью кода).
- `.gitignore` на уровне `dev/`: venv, node_modules, dist, веса моделей, локальный `.env`, файлы SQLite.

## Фаза 1 — БД НСИ: перенос схем в SQLite

**Статус: завершена.** Дата: 2026-08-01.

### Сделано

- Все 17 SQL-файлов обеих схем (`БД НСИ/` — 7 schema + 1 seed, `БД НСИ Аддитив/` — 8 schema + 2 seed) прочитаны полностью и адаптированы под SQLite в `backend/app/infrastructure/db/schema_sqlite/{metal,additive}/`.
- Синтаксические замены: `SERIAL` → `INTEGER PRIMARY KEY AUTOINCREMENT`, `JSONB` → `TEXT`, `TIMESTAMP NOT NULL DEFAULT now()` → `TEXT NOT NULL DEFAULT (datetime('now'))`, `TRUE`/`FALSE` → `1`/`0`, `COMMENT ON TABLE/COLUMN` перенесены в обычные SQL-комментарии над определением.
- **Устранена структурная проблема, которую SQLite не терпит, а PostgreSQL допускал:** `БД НСИ/schema/06_process.sql` в оригинале добавляет FK к уже созданной таблице `workpiece` через `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` (workpiece создаётся в файле 04, а `part`, на которую он ссылается, — в файле 06). SQLite не поддерживает добавление FK к существующей таблице. Решение: FK на `part(id)` объявлен сразу в `CREATE TABLE workpiece` (файл 04 SQLite-версии) — работает, потому что SQLite не проверяет существование таблицы, на которую ссылается FK, в момент `CREATE TABLE` (только при последующих `INSERT`/`UPDATE` с включённым `PRAGMA foreign_keys`), так что порядок файлов (part позже) не мешает.
- `backend/app/infrastructure/db/nsi_db.py`: `build_database()` создаёт SQLite-файл, применяет схему и seed по явно заданному порядку файлов (важно: `seed_application_rules.sql` в аддитивной схеме зависит от `seed_data.sql`, а не наоборот — при алфавитной сортировке ловилась `FOREIGN KEY constraint failed`, порядок исправлен на явный список, а не glob-сортировку по имени); `connect()` открывает соединение с `PRAGMA foreign_keys = ON`.
- **Обе схемы реально прогнаны на живом SQLite-файле** — впервые за всё время существования этих схем (README обеих исходных папок прямо указывал, что они не были прогнаны ни на PostgreSQL, ни где-либо ещё). Metal: 32 таблицы, additive: 34 таблицы, обе строятся из чистого файла за ~20 мс.
- Тесты (`pytest`, 6 новых тестов в `test_nsi_db.py`): обе схемы+seed загружаются без ошибок; ключевая compatibility-таблица `equipment_type_tooling_type` даёт непустой результат для реального типа станка из seed; FK `workpiece.part_id` реально проверяется (валидная вставка проходит, невалидный `part_id` вызывает `IntegrityError`); колонка `am_part.part_application_class_id`, добавленная через `ALTER TABLE ADD COLUMN` в 08-м файле, реально доступна; `application_material_recommendation` содержит посеянные строки; сборка без seed даёт пустые, но валидные таблицы. **Все 10 тестов backend (3 из Фазы 0 + 6 из Фазы 1 + 1 ранее) проходят.**
- `layout_schema` шаблонов `document_template` (metal) дополнен полным составом граф маршрутной/операционной карты по найденной структуре ГОСТ 3.1118-82/3.1404-86 (было — сокращённый список из оригинального seed, стало — полный: номер операции/перехода, содержание, оборудование, оснастка, режимы t/S/V/n, разряд работы, нормы времени То/Тв/Тшт/Тпз).
