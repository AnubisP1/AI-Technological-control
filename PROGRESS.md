### Сделано

- Дев-сервер проверен вживую через Playwright (headless Chromium, временно установлен и удалён — не входит в постоянные зависимости): страница рендерится, навигация между модулями работает, ошибок в консоли браузера нет. Скриншоты не сохранены в репозитории (не являются частью кода).

## Фаза 1 — БД НСИ: перенос схем в SQLite

**Статус: завершена.** Дата: 2026-08-01.

### Сделано

- Все 17 SQL-файлов обеих схем (`БД НСИ/` — 7 schema + 1 seed, `БД НСИ Аддитив/` — 8 schema + 2 seed) прочитаны полностью и адаптированы под SQLite в `backend/app/infrastructure/db/schema_sqlite/{metal,additive}/`.
- Синтаксические замены: `SERIAL` → `INTEGER PRIMARY KEY AUTOINCREMENT`, `JSONB` → `TEXT`, `TIMESTAMP NOT NULL DEFAULT now()` → `TEXT NOT NULL DEFAULT (datetime('now'))`, `TRUE`/`FALSE` → `1`/`0`, `COMMENT ON TABLE/COLUMN` перенесены в обычные SQL-комментарии над определением.
- **Устранена структурная проблема, которую SQLite не терпит, а PostgreSQL допускал:** `БД НСИ/schema/06_process.sql` в оригинале добавляет FK к уже созданной таблице `workpiece` через `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` (workpiece создаётся в файле 04, а `part`, на которую он ссылается, — в файле 06). SQLite не поддерживает добавление FK к существующей таблице. Решение: FK на `part(id)` объявлен сразу в `CREATE TABLE workpiece` (файл 04 SQLite-версии) — работает, потому что SQLite не проверяет существование таблицы, на которую ссылается FK, в момент `CREATE TABLE` (только при последующих `INSERT`/`UPDATE` с включённым `PRAGMA foreign_keys`), так что порядок файлов (part позже) не мешает.
- `backend/app/infrastructure/db/nsi_db.py`: `build_database()` создаёт SQLite-файл, применяет схему и seed по явно заданному порядку файлов (важно: `seed_application_rules.sql` в аддитивной схеме зависит от `seed_data.sql`, а не наоборот — при алфавитной сортировке ловилась `FOREIGN KEY constraint failed`, порядок исправлен на явный список, а не glob-сортировку по имени); `connect()` открывает соединение с `PRAGMA foreign_keys = ON`.
- **Обе схемы реально прогнаны на живом SQLite-файле** — впервые за всё время существования этих схем (README обеих исходных папок прямо указывал, что они не были прогнаны ни на PostgreSQL, ни где-либо ещё). Metal: 32 таблицы, additive: 34 таблицы, обе строятся из чистого файла за ~20 мс.
- Тесты (`pytest`, 6 новых тестов в `test_nsi_db.py`): обе схемы+seed загружаются без ошибок; ключевая compatibility-таблица `equipment_type_tooling_type` даёт непустой результат для реального типа станка из seed; FK `workpiece.part_id` реально проверяется (валидная вставка проходит, невалидный `part_id` вызывает `IntegrityError`); колонка `am_part.part_application_class_id`, добавленная через `ALTER TABLE ADD COLUMN` в 08-м файле, реально доступна; `application_material_recommendation` содержит посеянные строки; сборка без seed даёт пустые, но валидные таблицы. **Все 10 тестов backend (3 из Фазы 0 + 6 из Фазы 1 + 1 ранее) проходят.**
- `layout_schema` шаблонов `document_template` (metal) дополнен полным составом граф маршрутной/операционной карты по найденной структуре ГОСТ 3.1118-82/3.1404-86 (было — сокращённый список из оригинального seed, стало — полный: номер операции/перехода, содержание, оборудование, оснастка, режимы t/S/V/n, разряд работы, нормы времени То/Тв/Тшт/Тпз).

## Фаза 2 — Модуль 1.1: парсинг входной КД

**Статус: завершена.** Дата: 2026-08-01.

### Сделано

- **Доменный слой** (`app/domain/cad/`): `StepModel`/`BoundingBox`/`FaceColour`, `DrawingModel`/`TitleBlockFields`/`TechnicalRequirement`, `KdAnalysisResult`, порты `IStepParser`/`IDrawingParser` (Protocol) — реализации подключаются из `infrastructure`, домен о них не знает.
- **`RegexStepParser`** (`app/infrastructure/cad/regex_step_parser.py`) — baseline-реализация `IStepParser` по решению из QUESTIONS.md №1. Логика цепочки цвета (`STYLED_ITEM → ... → COLOUR_RGB`) взята за основу из `Литература/НПО 2026/src/step_parser.py`, но переписана под контракт этого проекта и дополнена раскодированием STEP-escape `\X2\HHHH...\X0\` — реальные тестовые STEP-файлы от C3D Converter/АСКОН кодируют кириллицу именно так, а не прямым UTF-8/windows-1251, как файлы SolidWorks, под которые был написан оригинальный парсер. Без этой доработки кириллические названия деталей не читались бы вовсе.
- **Валидация парсера на 3 реальных STEP-файлах**, а не только на синтетике:
  - `Кронштейн.STEP` (эталон из НПО 2026, известные значения) — 20 граней, цветовая схема точно совпала (9 фасок синих, 6 плоскостей голубых, 4 галтели зелёных, 1 отверстие красное).
  - Два fixture-файла из `КД для тестов/` (вал, шестерня) — оба успешно распарсены, bounding box вала по оси X (707.488 мм) совпал с размером 707±1 с чертежа этой же детали (перекрёстная проверка между STEP и PDF одного изделия).
- **`PdfDrawingParser`** (`app/infrastructure/cad/pdf_drawing_parser.py`) — извлечение основной надписи (ГОСТ 2.104) и технических требований из PDF с текстовым слоем через PyMuPDF. Поля штампа ищутся позиционно относительно текстовых меток ("Масштаб", "Формат", "Масса"), а не по хардкод-координатам — устойчиво к разным форматам листа.
  - **Существенная итерация на реальных данных**: первая версия давала неверные значения на обоих fixture (перепутанные поля, значения-лейблы вместо значений, часть текста пропущена) — оказалось, что метки в штампе могут стоять и слева, и сверху от значения в зависимости от графы, наименование детали может переноситься на несколько строк с продолжением со строчной буквы, а материал иногда разбит на две строки ("Сталь МАРКА" / "ГОСТ N") вместо одной. Все случаи выявлены и исправлены именно потому, что тестировалось на двух по-разному сверстанных реальных чертежах, а не на одном.
  - Технические требования нумеруются последовательно с проверкой (не даёт ложных срабатываний на даты вида "24.02.2023" или допуски вида "0.025", которые синтаксически похожи на "число.текст").
  - `has_text_layer` явно сигнализирует отсутствие текстового слоя (скан) — не подменяется тихой выдачей пустых полей, которая была бы неотличима от чертежа, где поля реально отсутствуют.
- **`KdAnalysisService`** (`app/services/`) — оркестрирует парсер чертежа, детектор видов и парсер STEP-модели через `worker_pool.run_heavy`, чтобы разбор не блокировал event loop.
- **`POST /kd/analyze`** — эндпоинт загрузки чертежа (опционально) и STEP-модели (опционально, для пластиковых изделий по ТЗ — только STEP без чертежа), возвращает структурированный JSON (включая детекцию видов).
- Тесты (`pytest`, 16 новых на первом проходе): 6 для STEP-парсера, 6 для PDF-парсера, 3 для эндпоинта, 1 нагрузочный CPU-тест.
- Закрыт отложенный пункт DoD Фазы 0: нагрузочный тест с реальной вычислительной нагрузкой (`test_cpu_budget_load.py`) — подтверждает, что парсинг не порождает дополнительных потоков сверх бюджета ресурс-губернатора.

### Продолжение Фазы 2 (по решениям пользователя от 2026-08-01)

Пользователь принял три решения: (1) отменить парсинг спецификации — не нужен для формирования ТД; (2) реализовать детекцию видов на чертеже, используя дополнительные чертежи из `КД для тестов/Детали из металла/Архив/` для тестирования; (3) для OCR сканов не обязательно следовать архитектуре CRAFT+CRNN из статьи Белоусова — важен результат, а не конкретный метод.

- **Детекция видов на чертеже** (`app/domain/cad/view_detection_model.py`, `view_detector_port.py`) — единый порт `IViewDetector`, две реализации:
  - **`VectorViewDetector`** — двухпроходная пространственная кластеризация bounding box'ов векторных путей PDF (`page.get_drawings()`), без внешних ML-зависимостей. Проход 1: плотная кластеризация штрихов в протокластеры (фиксированный порог 15pt). Проход 2: укрупнение протокластеров порогом, пропорциональным их собственному размеру (0.3 × диагональ меньшего) — это ключевое решение после итерации: фиксированный порог в пунктах PDF давал от 2 до 36 "видов" в зависимости от чертежа (не масштабируется между форматами листа A3/A2), относительный порог даёт стабильные 2-6 областей на всех 7 проверенных реальных чертежах (2 основных fixture + 5 из `Архив/`, включая дополнительные, не участвовавшие в калибровке алгоритма — тест на переобучение порогов).
  - **`RasterViewDetector`** — рендер страницы в растр + OpenCV (`connectedComponentsWithStats` после Otsu-бинаризации и дилатации) для сканов. Готовая библиотека вместо своей CV-модели (правило ТЗ п.4).
  - **`AutoViewDetector`** — выбирает стратегию по числу векторных путей на странице (≥20 → вектор, иначе растр).
- **OCR для сканов** — `OcrDrawingParser` на Tesseract (`pytesseract`), не CRAFT+CRNN. Требует установленного бинаря `tesseract` с языковым пакетом `rus` (dev-time зависимость: `brew install tesseract-lang` на macOS). Рендер в 400 DPI + бинаризация Отсу перед OCR (PSM 11 — разрозненный текст) ощутимо улучшают результат по сравнению с прямым OCR необработанного цветного рендера — проверено экспериментально на синтетическом "скане" реального fixture.
  - **Рефакторинг для переиспользования**: логика извлечения штампа/ТТ вынесена из `PdfDrawingParser` в отдельный модуль `stamp_extraction.py`, работающий с абстрактным списком строк `(x0,y0,x1,y1,text)` — теперь и текстовый слой PDF, и результат OCR проходят один и тот же путь извлечения после получения строк, без дублирования позиционной эвристики.
  - **`AutoDrawingParser`** — выбирает PDF-текст или OCR по наличию текстового слоя (≥20 символов).
  - Качество OCR ниже текстового слоя (реальное ограничение технологии на плотных чертежах, не дефект парсера) — задокументировано, тесты проверяют, что конвейер работает end-to-end, а не точное совпадение полей.
- **Побочная находка про CPU-бюджет**: `cv2.setNumThreads()` не имеет эффекта на сборках OpenCV с параллельным бэкендом GCD (типично для macOS ARM, подтверждено через `cv2.getBuildInformation()`) — документированное ограничение самого OpenCV, не баг ресурс-губернатора. Governor всё равно вызывает `cv2.setNumThreads()` (реально работает на сборках с TBB/OpenMP — Linux/Windows), тест проверяет применимый на любой платформе инвариант, а не факт ограничения.
- Тесты: +9 (детекция видов на 2 доп. архивных чертежах + границы регионов + raster-путь на синтетическом скане + автовыбор для обоих путей + OCR end-to-end + auto-parser routing), +1 обновлённый (ресурс-губернатор), обновлён тест эндпоинта под новое поле `view_detection`. **Все 36 backend-тестов проходят.**

## Открытые архитектурные решения, принятые в ходе работы

См. `QUESTIONS.md` — все пункты закрыты решениями (не пользователем поштучно, а с явным делегированием "поступай как считаешь нужным" по вопросам 1, 2, 7, 8). Кратко:
- Backend: Python 3.11 + FastAPI (не Python 3.14, чтобы оставить путь к `pythonocc-core` открытым).
- STEP-парсинг: через интерфейс `IStepParser`, первая реализация — адаптация regex-парсера из `Литература/НПО 2026/src/step_parser.py`, вторая (по необходимости) — `pythonocc-core`.
- LLM: без резервирования весов заранее; текст отчётов/карт на первых фазах — шаблонный, ruT5/FRED-T5+LoRA (из статьи Белоусова) подключается на Фазе 3, если правил недостаточно.
- Метрики Модуля 3.2 (риски/брак/стоимость) — демонстрационная эвристика с явной пометкой в UI, не производственный расчёт.
- Спецификация (БОМ) — отменена явным решением пользователя, не входит в объём проекта.
- Детекция видов на чертеже — две реализации (векторная кластеризация + растровая CV-сегментация) за одним портом с автовыбором, а не единственный универсальный алгоритм.
- OCR сканов — готовая библиотека Tesseract вместо собственной CRAFT+CRNN-архитектуры, по явному решению пользователя ("не принципиально, главное чтобы работало").
